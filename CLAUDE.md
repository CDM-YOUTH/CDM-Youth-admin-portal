# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single TanStack Start (React 19 + Vite) app for the Catholic Diocese of Murang'a Youth Office. It serves two
surfaces from one codebase and one Supabase Postgres database:

- **Admin portal** (`/admin/*`) — staff dashboard for youth records, enrollment, leaders, CUSA, events, mission
  week; formation/welfare/uniforms/reports/users/audit exist as routes and DB modules but are commented out of the
  sidebar nav (`src/components/admin/layout/admin-sidebar.tsx`) — not currently exposed to users.
- **Youth portal** (`/portal/*`) — self-service mobile-first pages for youth to enroll, browse events, and manage
  their account.

Deploys to Cloudflare Workers via `@cloudflare/vite-plugin` (see `wrangler.jsonc`). Scaffolded with
`@lovable.dev/vite-tanstack-config`, which bundles TanStack Start, React, Tailwind v4, `vite-tsconfig-paths`, and
Cloudflare plugins — **do not** add any of those plugins manually in `vite.config.ts`, it will duplicate them and
break the build. Additional Vite config goes through `defineConfig({ vite: { ... } })`.

## Commands

```bash
npm run dev         # vite dev — local dev server
npm run build        # production build
npm run build:dev    # build in development mode
npm run preview      # preview a production build
npm run lint         # eslint .
npm run format       # prettier --write .
```

There is no test suite/runner configured in this repo (no `test` script, no `*.test.*`/`*.spec.*` files).

Database migrations live in `supabase/migrations/*.sql`, applied via `scripts/apply-migration.mjs` (invoked
manually — check the script before assuming Supabase CLI is set up). Other one-off scripts (`seed-admin.mjs`,
`seed-org.mjs`, `assign-role.sql`, `fix-login.sql`, `setup-all.sql`) live in `scripts/`.

## Architecture

### Two Supabase access paths — know which one you're in

There are three ways code talks to Supabase, each for a different trust level. Picking the wrong one either breaks
RLS-protected data or leaks a service-role key to the browser:

1. **`@/integrations/supabase/client`** (`supabase`) — anon/publishable key, browser + SSR safe, subject to Row
   Level Security. This is what almost all `src/lib/db/**` query modules and route components use directly.
2. **`@/integrations/supabase/client.server`** (`supabaseAdmin`) — service-role key, **bypasses RLS**. Server-only
   (throws if misused client-side isn't enforced by code — enforced by *never importing it from a client component*).
   Use only in server functions/API routes for trusted admin operations.
3. **`@/integrations/supabase/auth-middleware`** (`requireSupabaseAuth`) — TanStack Start server middleware that
   validates a `Bearer` token from the request and hands `{ supabase, userId, claims }` to `next()`, where that
   `supabase` client is scoped to the calling user's token (RLS applies as that user).

The files under `src/integrations/supabase/` are marked `// This file is automatically generated. Do not edit it
directly.` — despite that comment, changes here are made manually in this repo; treat the comment as inherited
boilerplate, not an actual constraint. `src/routeTree.gen.ts` **is** genuinely auto-generated by the TanStack
Router Vite plugin from files in `src/routes/` — never hand-edit it.

### API routes (`src/routes/api/**`)

Server API endpoints use `createAPIFileRoute` (TanStack Start file-based API routes) and follow one consistent
pattern, built from helpers in `src/lib/api/server-client.ts`:

```ts
export const APIRoute = createAPIFileRoute("/api/youths")({
  GET: async ({ request }) => {
    const guard = await guardRequest(request);       // auth + rate limit + role/scope lookup
    if ("error" in guard) return guard.error;
    // ... build a Supabase query, apply applyCallerScope() to enforce org scoping ...
    return jsonOk({ data, total, page, size });        // or jsonError(message, status)
  },
});
```

Key pieces from `src/lib/api/`:
- `auth.ts` — `verifyAuth(request)` validates the `Authorization: Bearer <token>` header against Supabase and
  returns claims.
- `rate-limiter.ts` — in-memory sliding-window limiter keyed by `userId` (120 req/60s). Explicitly **no
  `setInterval`** (banned on Cloudflare Workers) — pruning happens opportunistically on each check.
- `server-client.ts` — `guardRequest()` composes auth + rate limit + role/org-scope lookup in one call;
  `applyCallerScope()` forces a scoped user's query params to match their assigned deanery/parish, preventing a
  scoped staff account from reading outside their org; `parsePagination()`, `jsonOk()`, `jsonError()` are shared
  response helpers.
- `fetch-api.ts` — client-side counterpart (`apiFetch`, `apiGet`, `buildParams`) that attaches the current
  session's access token to outgoing requests.

Not every domain goes through `/api/**` — many admin pages call `src/lib/db/**` query modules directly from
components using the anon-key `supabase` client and rely on RLS. The `/api/**` path is used where server-side
auth/rate-limiting/org-scoping matters (e.g. cross-org queries, Google Sheets sync). When adding a new endpoint,
follow whichever pattern the sibling code in that domain already uses.

### Data layer (`src/lib/db/**`)

Query modules organized by domain, each exporting typed row types and fetch/mutate functions built on the
`supabase` client:
- `youth-records/` — `youths.ts`, `enrollments.ts`, `leaders.ts`, `cusa.ts`, `profiles.ts`, `import.ts` (bulk CSV
  import)
- `activities/` — `events.ts`, `mission.ts`
- `ministry/` — `formation.ts`, `welfare.ts`
- `assets/` — `uniforms.ts`, `uniform-sales.ts`, `uniform-stock-entries.ts`
- `org.ts` — deaneries/parishes/outstations tree (`fetchOrg`), used to resolve org names/IDs across most other
  modules
- `analytics.ts` / `analytics-rpc.ts` — dashboard aggregates, several backed by Postgres RPC functions
- `audit.ts`, `portal.ts`

Route components query through these modules with `@tanstack/react-query` (not raw `useEffect`/`fetch`).

### Org scoping model

The diocese hierarchy is **deanery → parish → outstation**. A staff user's assigned scope (from their `profiles`
row, joined to `user_roles`) restricts which org units they can see/query — enforced both by RLS policies in the
DB and, for `/api/**` routes, explicitly via `applyCallerScope()`. `src/lib/hooks/use-admin-scope.ts` exposes the
logged-in user's scope to the admin UI via `AdminScopeCtx` (populated once in `src/routes/admin.tsx`'s
`beforeLoad`/component and read with `useAdminScope()`).

### Routing

File-based routing via `@tanstack/react-router`'s Vite plugin — filenames map to paths using dots as path
separators (e.g. `admin.event-checkin.$eventId.tsx` → `/admin/event-checkin/:eventId`). `src/routes/admin.tsx` is
the layout route for all `/admin/*` pages: it gates access with a client-only session check in `beforeLoad`
(explicitly skipped during SSR — see the comment in that file for why) and renders the sidebar/topbar shell around
`<Outlet />`. `src/routes/__root.tsx` sets up the HTML shell, global `QueryClientProvider`, and toaster.

### Auth

Supabase Auth. Admin routes redirect to `/login` client-side when there's no session (see `admin.tsx` above).
Youth portal auth (`portal.auth.tsx`) is a separate, more self-service flow. Server-side, staff role and org scope
are read from `user_roles` + `profiles` tables (see `guardRequest()` above), not from JWT claims alone.

### UI components

`src/components/ui/**` is shadcn/ui (`components.json`: style `new-york`, Tailwind v4 with CSS variables, no RSC).
Regenerate/add components with the shadcn CLI rather than hand-rolling primitives — it targets the `@/components/ui`
alias family configured there (`components`, `utils`, `ui`, `lib`, `hooks` all under `@/*`, mapped in
`tsconfig.json`). Domain-specific composites live in `src/components/admin/composables/**` (shared forms, table
filters/pagination, pickers) and are reused across admin pages rather than duplicated per route.

### Exports

`export-xlsx.ts` (ExcelJS) and PDF export (jsPDF + `jspdf-autotable`) are used for register/report exports (e.g.
event registration lists) — check existing usages in `admin.events.tsx`/event components before adding a new export
path, since column layout and formatting conventions (e.g. Kenyan phone formatting, `Africa/Nairobi` timestamps via
`titleCase`/`formatPhone` in `src/lib/utils.ts`) are established there.

### Google Sheets integration

`src/lib/google/sheets-fetch.ts` + `sheets.ts` and `src/routes/api/sheets/**` sync event registration data
(currently the Leadership Workshop event) to a Google Sheet using a service-account key
(`GOOGLE_SA_KEY_BASE64`, `GOOGLE_SHEETS_ID` env vars). Server-only.

## Environment variables

Defined in root `.env` (client-exposed vars are prefixed `VITE_`; server-only vars are not):
`SUPABASE_URL`/`VITE_SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`/`VITE_SUPABASE_PUBLISHABLE_KEY`,
`SUPABASE_SERVICE_ROLE_KEY` (server-only, admin client), `SUPABASE_PROJECT_ID`, `GOOGLE_SA_KEY_BASE64`,
`GOOGLE_SHEETS_ID`, `LEADERSHIP_WORKSHOP_EVENT_ID`. Note: `.env` is currently tracked in git in this repo (contrary
to `.gitignore`'s own `.env` rule) — be careful not to add any new secret to it without checking with the user
first, since it's already committed history.

split into a dedicated `cdm-backend` service plus independent frontend repos, and a security/go-live audit. Both
